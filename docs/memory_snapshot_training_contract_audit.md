# 内存快照训练前合同审计

本审计针对 `game_environment/craftground_mod/MemorySnapshotStore.kt` 当前实现。结论只覆盖已经由源码或真实测试证明的状态，不把完整玩家 NBT 等同于完整世界重放。

## 当前能力边界

| 状态类别 | 当前实现 | 证据 | 训练前结论 |
|---|---|---|---|
| 区域方块、流体、方块实体 NBT | `StructureTemplate.saveFromWorld` 与 `place` | 方块、水、箱子和熔炉真实断言已通过 | 可用于静态地形、容器和采集课程 |
| 玩家位置、视角、速度、背包、生命、饥饿、经验、效果 | 玩家 NBT，加状态效果显式恢复和网络同步 | 连续八次真实恢复测试已通过观测字段 | 可用于同维度、未骑乘、未睡眠的单玩家课程 |
| 客户端和服务端 GUI | 加载时关闭客户端画面和服务端容器 | 源码可见；移动探针覆盖输入是否被吞 | 可作为中和策略，不能宣称恢复了原 GUI 状态 |
| 普通实体 | 保存时 `includeEntities=false`，加载时 `setIgnoreEntities(true)` | 源码明确排除 | 不可用于依赖生物、掉落物、船、矿车和弹射物的公平 batch |
| 方块计划刻和流体计划刻 | `StructureTemplate` 不保存调度队列 | 当前没有额外捕获逻辑 | 不可用于活塞、红石时序、流体传播、作物/机器时序的严格重放 |
| 跨维度状态 | 加载模板使用玩家当前 `serverWorld`，没有显式跨世界传送 | 源码调用顺序明确 | 只支持同维度恢复；跨维度前后分别捕获快照 |
| 世界全局状态 | 未捕获游戏时间、天气、规则、世界边界、袭击等 | 快照对象只有模板和玩家状态 | 由课程夹具固定，或者列为非确定性因素 |

## `readNbt` 风险

直接把 `player.writeNbt` 的完整结果传给仍在线的 `ServerPlayerEntity.readNbt`，恢复范围大于当前测试观察到的字段。NBT 还可能包含睡眠、传送门冷却、火焰、坠落距离、能力、末影箱、配方或其他版本相关字段。网络连接、当前容器、载具关系和所在 `ServerWorld` 又不是普通 NBT 字段能够原子替换的对象。

因此当前合同必须满足以下约束：

1. 保存和恢复发生在同一个 Minecraft 版本、同一个 JVM、同一个玩家实体和同一个维度。
2. 捕获前玩家必须离开载具、床和传送门过渡状态，落地或处于课程明确允许的稳定运动状态。
3. 捕获和恢复时不保留打开的容器语义；恢复后的规范状态是 GUI 关闭。
4. 每次恢复后验证位置、视角、背包、选中槽、生命、饥饿、效果和移动探针。关键精密课程还应验证速度与落地状态。
5. Minecraft 或 Yarn 映射升级后重新运行真实恢复测试，不能仅以编译通过继承结论。

长期建议是从完整 `readNbt` 改为字段白名单恢复。白名单应显式覆盖课程需要的玩家状态，并排除 UUID、维度身份、网络生命周期、载具和睡眠等需要专用 API 的状态。

## 训练前最低合同

当前实现可以先支持以下课程：

- 同维度静态地形中的移动、观察、方块采集、制作和容器交互。
- 不依赖普通实体复位的探索和导航。
- 玩家资源、装备和效果能够由连续恢复审计覆盖的课程。
- 每条候选执行前都通过同起点字段校验和动作探针的 `batch=8`。

以下课程在扩展前必须隔离，不能进入相对优势训练主池：

- 铁傀儡、烈焰人、末影人、村民、末影龙等实体战斗。
- 船、矿车、掉落物、箭和其他实体机制。
- 刷铁机以及依赖实体记忆、村庄兴趣点和计划刻的自动化装置。
- 传送门穿越过程、跨维度同快照恢复。
- 落沙、流体传播、活塞和严格红石时序课程。

隔离不代表这些任务不可完成。它只表示当前快照不能保证八条候选拥有等价初态。正式支持实体课程时，最低实现应捕获区域内实体的类型、UUID 映射、位置、运动、生命、装备、AI/记忆和乘客关系；加载前删除当前区域受管实体，再以新的运行时 UUID 恢复并重建引用，最后验证数量、类型和关键状态，避免实体重复。

## 必须通过的门禁

| 门禁 | 通过标准 |
|---|---|
| 玩家连续恢复 | 至少 `8/8`，规范字段在容差内一致 |
| GUI 中和 | 容器打开后恢复，动作探针能够移动且不会修改旧容器 |
| 同维度约束 | 快照记录维度 ID；加载时不一致应拒绝，而不是尝试放置模板 |
| 实体隔离 | 课程声明依赖普通实体时，调度器在实体快照合同完成前拒绝进入公平 batch |
| 计划刻隔离 | 课程声明依赖流体、红石或方块时序时，拒绝严格重放评价或使用完整世界副本 |
| 状态审计 | 每条轨迹保存恢复前后的结构化差异；任何起点偏差使整批失效 |
| 版本门禁 | Minecraft、CraftGround 或映射版本变化后重新执行真实测试 |

## 推荐实现顺序

1. 先给快照元数据加入维度 ID 和能力标志，在加载时快速失败。这是低成本的错误隔离。
2. 把课程需求声明为 `static_world`、`entities`、`scheduled_ticks`、`cross_dimension` 等能力，由调度器匹配快照后端。
3. 实体课程优先采用“一条候选一个独立世界副本或进程”的基线，建立正确性结果后再优化为内存实体快照。
4. 对计划刻优先使用完整世界保存/恢复或独立进程基线。直接操作服务端 tick scheduler 属于版本敏感实现，需要单独测试。
5. 完成实体恢复后，至少验证生物生命与装备、掉落物、船与乘客、弹射物清理、村民和铁傀儡重复恢复，再开放对应课程族。

当前训练前可接受结论是：静态世界、同维度、单玩家课程已经具备可验证的快照基础；普通实体、计划刻和跨维度课程仍需隔离。这一边界不影响观察驱动课程生成，但会限制哪些课程能够进入公平的相对优势执行。
