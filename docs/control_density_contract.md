# 控制契约：开放帧率与三类坐标

草案，待修改。目标是把 Lumine 的动作表示从"一个游戏一套配置"推广到**帧率可声明**、
**键鼠与手柄同串**。

## 与 Lumine 原文的差异

Lumine（arXiv 2511.08892）的实际规格是固定的：感知 5Hz，电机 30Hz，每窗口恒 6 个
33ms chunk，鼠标只有相对增量（整数，开区间 ±1000 像素），滚轮 ±5，无手柄。33ms 的
依据是实测人类 keyup→keydown 最小间隔约 40ms。

| 维度 | Lumine | 本契约 |
|---|---|---|
| 感知周期 | 固定 200ms | 声明式，环境给定 |
| 电机粒度 | 固定 33ms × 6 | 声明式，chunk 数随之变 |
| 视角单位 | 像素 | 毫度（milli-degree） |
| 坐标种类 | 只有相对增量 | 相对增量 / 绝对位置 / 轴状态 |
| 设备 | 仅键鼠 | 键鼠与手柄共用同一串 |

**为什么把像素换成毫度**：像素量依赖 DPI 与游戏内灵敏度，同一个 `92` 在两台机器上转
的角度不同。Lumine 只跑一个游戏一套配置，所以像素够用；一旦要跨设备（手柄没有"像素"
概念）和跨游戏，唯一稳定的量是角度。毫度取整后精度 0.001°，远超 MineStudio 的
0.15°/像素量化步长，不引入新的精度损失。

## 一、三类坐标角色

三类是按**语义角色**分的，不是按设备分的。同一个串在键鼠和手柄上都合法，由绑定档
（binding profile）决定怎么落到实际设备。

### 1. `aim` — 相对增量

视角/准星控制。窗口内累计的相对转动量，单位毫度。

- 键鼠：毫度 ÷ 每像素度数 → 像素增量，在窗口内平滑铺开执行（同 Lumine）
- 手柄：毫度 ÷ 窗口时长 → 度/秒，再除以该档位的最大角速度 → 右摇杆偏移量

取值域 `aim` 每轴 ±180000（半圈）。TODO: 是否该按窗口时长缩放上限，见待定决策 3。

### 2. `cur` — 绝对位置

菜单/背包里的光标位置。归一化到 `0..1000` 的整数网格，与实际分辨率解耦。

- 键鼠：直接映射为屏幕绝对坐标，一步到位
- 手柄：无绝对指针，需由绑定档把目标位置转成"虚拟光标以受限速度移向目标"的多步逼近；
  单窗口内可能到不了，属正常，下一窗口继续

绝对而非相对，是因为 UI 交互的目标是"点到那个格子"，相对增量在这里会累积漂移。

### 3. `mov` — 轴状态

持续的方向性推量（移动、油门、扳机）。`<方向档> <幅度档>` 两个整数。

- 键鼠：方向档 → WASD 组合（8 向）；幅度档只有"是否疾跑"两级可表达
- 手柄：方向档 → 摇杆角度，幅度档 → 摇杆偏移量，可表达连续中间态

方向档数与幅度档数由绑定档声明。键鼠档下幅度档 >2 的部分不可表达，绑定档需声明如何
降级（取最近可表达值）。

## 二、开放帧率

时间布局由环境在 prompt 里声明，不硬编码在格式里：

    perception_ms   一次前向覆盖的时长
    chunk_ms        单个电机 chunk 的时长
    chunk_count     = perception_ms / chunk_ms，必须整除

**控制密度**即 `1000 / chunk_ms`（chunk/秒）。它是一个真实的权衡轴：

| chunk_ms | 密度 | 单窗口 chunk 数 (200ms) | 代价 |
|---|---|---|---|
| 50 | 20Hz | 4 | token 少；短于 50ms 的点击丢失 |
| 33 | 30Hz | 6 | Lumine 默认；贴合人类 40ms 最小间隔 |
| 16 | 60Hz | 12 | token 翻倍；超出人类可分辨，多为噪声 |

上限受人类操作物理极限约束：keyup→keydown 实测下限约 40ms，所以 `chunk_ms < 20` 基本
只在拟合采集噪声。下限受任务约束：需要精确计时的操作（格挡、连招）撑不住 50ms 粒度。

MineStudio 数据源是 20Hz（50ms/帧），所以从它构建时 `chunk_ms` 只能取 50 的整数倍。
更细的粒度需要更高帧率的数据源。

## 三、动作串语法

    <|action_start|>
    aim <Δyaw> <Δpitch> <Δscroll>
    cur <x> <y>
    mov <方向档> <幅度档>
    ; <键...> ; <键...> ; ...
    <|action_end|>

三个坐标行都是**可选的**，缺省即该角色本窗口无输入。这样菜单里不必写 `aim`，战斗中
不必写 `cur`，token 不浪费在恒零的字段上。键 chunk 部分与 Lumine 完全一致：run-length
语义，相邻 chunk 重复即保持按下，缺席即松开，无时长数值、无按下/松开事件 token。

单行紧凑形式（**TODO: 二选一，见待定决策 2**）：

## 四、待定决策

以下几处我给了倾向，但都由你定。

**1. 是否回显 chunk_count**
倾向不回显。环境已知该值，回显只在模型自己出错时才有信息量，而那种情况解码器按
`expected_chunks` 对齐已经能救回来（现有 `decode_lumine_action` 就这么做的）。

**2. 多行还是单行**
倾向单行。多行可读性好，但每个换行都是 token，且训练时 chat template 对换行的处理
容易引入不一致。单行 + 前缀标签（`aim` / `cur` / `mov`）已经足够区分。

**3. aim 上限是否随窗口时长缩放**
倾向固定 ±180000 不缩放。缩放能让"上限=物理可达上限"，但会让同一个数值在不同帧率下
含义不同，破坏跨帧率迁移——而跨帧率迁移正是开放帧率的目的。固定域下短窗口用不到大值，
浪费的是值域而非正确性。

**4. `mov` 与 WASD 是否并存**
两条路都能表达移动，同时存在会产生歧义（模型可以任选，训练信号被劈开）。倾向：
键鼠档下只用 WASD 键（`mov` 不出现），手柄档下只用 `mov`（方向键不出现），由绑定档
二选一而非同时开放。**这条影响最大，需要你确认。**

**5. 视角是否离散化**
本契约仍是自由整数（回归任务）。你之前否掉了 mu-law 分箱，此处沿用。若后续要改，
毫度单位对分箱是友好的——`bin = mu_law(milli_degree)` 直接可算。
