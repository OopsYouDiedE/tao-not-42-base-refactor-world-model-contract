# 控制契约：开放帧率与键鼠手柄统一

已定稿。相对 Lumine 三处改动，都不影响 run-length 编码语义：

1. 带值操作统一成**命名 token + 值**，作用域一律是**所在 tick**，位置式 header 取消
2. 手柄专用键统一成 `XYAB` 等常用名，按下类（含 `LSHold`）就是普通键名
3. chunk 数不固定，模型爱出几个出几个

## 与 Lumine 原文的差异

Lumine（arXiv 2511.08892）规格是硬固定的：感知 5Hz、电机 30Hz、每窗口恒 6 个 33ms
chunk、header 是位置式三整数（鼠标 `Δx Δy` 开区间 ±1000 像素 + 滚轮 ±5）、**无手柄**。
33ms 粒度有实证依据——实测人类 keyup→keydown 最小间隔约 40ms。

| 维度 | Lumine | 本契约 |
|---|---|---|
| 带值操作 | 位置式 header，恒 3 整数 | 命名 token，按需出现 |
| 值的作用域 | 整个窗口（200ms 平铺） | 所在 tick |
| 视角输入 | 仅鼠标像素 | `Mouse` 像素 或 `LS`/`RS` 摇杆 |
| 手柄 | 无 | `XYAB` 等，与键盘键同等对待 |
| chunk 数 | 固定 6 | 不限 |

## 一、统一形式

    <|action_start|> ; W Mouse 10 20 ; W ; W Scroll 5 ; RS 0 100 A <|action_end|>

带值 token 后跟固定个数的整数，与键名混排在同一个 chunk 里：

| token | 值 | 含义 | 缺席时 |
|---|---|---|---|
| `Mouse` | 2 | 像素增量 Δx Δy，本 tick 内移动这么多 | 无移动 |
| `Scroll` | 1 | 滚轮档数，等价于重复写 `Scroll` 该次数 | 无滚动 |
| `LS` / `RS` | 2 | 摇杆偏移量，每轴 −100..100 | **0 0（回中）** |

一切都是 tick 内操作，**缺席即零**，一条规则覆盖全部 token（键、增量、计数、杆位），
解码器不需要为任何 token 开特例。`LS 0 100` 就是本 tick 内 Y 方向满偏，持续本 tick，
下个 tick 不写就回中。

`Scroll 5` 与连写五次 `Scroll` 完全等价，随模型方便。`Mouse` 与 `LS`/`RS` 没有这种
等价——它们的值不是次数。

摇杆取 −100..100（百分比偏移）。真实手柄轴约 8 位精度（±127），死区通常吃掉头 10–15%，
所以 1% 分辨率不损失可用信息。

### 值挪到 tick 级的两个实测后果

在 10xx 的 21.7 万帧上量过：

**鼠标 token 变多，但只多约 2 倍，不是 4 倍。** 逐帧相机增量非零的帧只占 **52.4%**——
玩家有近一半时间不动视角。所以 4-chunk 窗口里平均出现约 2.1 个 `Mouse`，而非 4 个。

**±999 钳位在 tick 级基本失效，退化成安全栏。** 单帧超 999 的比例是 **0.0005%**
（约 20 万帧 1 帧），而 4 帧窗口级是 0.0534%。单帧 |yaw| 中位数 0，p99 只有 146，
最大 1093。也就是说钳位几乎不再改动任何值，绝大多数 `Mouse` 值是 1–3 位数。
钳位保留，但它现在的作用是挡住异常值，不再是有效量化器。

## 二、手柄键名

按下类一律当普通键名，与键盘键同等，不需要任何特殊机制：

| 类别 | 键名 |
|---|---|
| 面键 | `A` `B` `X` `Y` |
| 肩键 | `LB` `RB` |
| 扳机 | `LT` `RT` |
| 摇杆按下 | `LSHold` `RSHold` |
| 功能 | `Start` `Select` |
| 十字键 | `Up` `Down` `Left` `Right` |

手柄键名总数比键盘常用集多一些，但不影响任何机制——run-length 对键名数量不敏感。

`A`/`B`/`X`/`Y` 与键盘同名字母键在同一命名空间里会撞。一次会话只用一种设备档，实际
不会同时出现，但**解码白名单必须按设备档给**，不能给全集——否则手柄档下模型吐出键盘
的 `A` 会被当成面键 A 接受。

`LT`/`RT` 先当二值键。要模拟量时按带值 token 处理即 `LT 60`，不破坏现有形式。

鼠标键名统一成 CamelCase：`MouseLeft` / `MouseRight`（原 `mouse_left` / `mouse_right`），
与 `LSHold` 等风格一致。纯改名，无语义影响。

## 三、chunk 数不固定

`expected_chunks` 从"强制对齐"降级为"可选校验"：给了就补齐/截断，不给就按模型实际
吐出的个数走。默认不给。

run-length 语义本来不依赖 chunk 总数——键在相邻 chunk 连续出现即保持按下、缺席即松开，
对任意长度都成立。放开长度不改语义，只需解码器别再强行对齐。

**超出期望的 chunk 直接丢弃**，不延到下个窗口执行：延后会让动作与观测的错位越积越多，
而 Lumine 本来已有约 200ms 观测滞后。少出的 chunk 等价于剩余时间全松开，可接受。

时间布局由环境在 prompt 里声明，模型不预测：`chunk_ms` 是单 chunk 时长，`chunk_count`
是建议值而非硬约束。**控制密度** = `1000 / chunk_ms`：

| chunk_ms | 密度 | 代价 |
|---|---|---|
| 50 | 20Hz | token 少；短于 50ms 的点击丢失 |
| 33 | 30Hz | Lumine 默认；贴合人类 40ms 最小间隔 |
| 16 | 60Hz | token 翻倍；超出人类可分辨，多为噪声 |

`chunk_ms < 20` 基本只在拟合采集噪声。反向下限受任务约束：需要精确计时的操作（格挡、
连招）撑不住 50ms 粒度。

硬约束：**MineStudio 是 20Hz 源（50ms/帧），从它构建时 `chunk_ms` 只能取 50 的整数倍**。
更细粒度需要更高帧率的数据源。

**训练先按单一 `chunk_ms`**，把变长当推理侧容错而非能力。若训练全定长，放开长度只在
推理侧生效，模型不会真的用它；要让它成为能力，训练集得含多种 `chunk_ms` 的样本，而这
需要更高帧率的数据源。

视角沿用自由整数回归，不分箱。
