# 控制契约：开放帧率与键鼠手柄统一

草案，待修改。三处改动，都不影响 run-length 编码语义：

1. 带值操作统一写成**命名 token + 值**（`Mouse 10 20`、`Scroll 5`、`RS -100 100`），
   与键名同处一个流，原来的位置式 header 取消
2. 手柄专用键统一成 `XYAB` 等常用名，按下类（含摇杆按下 `RSHold`）就是普通键名
3. chunk 数不固定，模型爱出几个出几个

## 与 Lumine 原文的差异

Lumine（arXiv 2511.08892）的规格是硬固定的：感知 5Hz、电机 30Hz、每窗口恒 6 个 33ms
chunk、header 是位置式三整数（鼠标 `Δx Δy` 开区间 ±1000 像素 + 滚轮 ±5）、**无手柄**。
33ms 粒度有实证依据——实测人类 keyup→keydown 最小间隔约 40ms。

| 维度 | Lumine | 本契约 |
|---|---|---|
| 带值操作 | 位置式 header，恒 3 个整数 | 命名 token，按需出现 |
| 视角输入 | 仅鼠标像素 | `Mouse` 像素 或 `LS`/`RS` 摇杆 |
| 值的作用域 | 整个窗口 | 所在 chunk |
| 手柄 | 无 | `XYAB` 等，与键盘键同等对待 |
| chunk 数 | 固定 6 | 不限 |

## 一、统一形式

    <|action_start|> ; W Mouse 10 20 ; W ; W Scroll 5 ; RS -100 0 A <|action_end|>

带值 token 后跟固定个数的整数，与键名混排在同一个 chunk 里：

| token | 值 | 含义 |
|---|---|---|
| `Mouse` | 2 个 | 像素增量 Δx Δy |
| `Scroll` | 1 个 | 滚轮档数，等价于重复写 `Scroll` 该次数 |
| `LS` / `RS` | 2 个 | 摇杆偏移量，每轴 −100..100 |

`Scroll 5` 与连写五次 `Scroll` 完全等价，随模型方便。`Mouse` 与 `LS`/`RS` 没有这种
等价——它们的值不是次数。

值落在**所在 chunk** 而非整个窗口。这比 Lumine 的窗口级 delta 更细：Lumine 把一个
`Δx` 平铺到 200ms 上执行，此处模型可以在窗口内塑造视角轨迹（先快后慢、中途反向）。
代价是持续移动时每个 chunk 都要写一遍。

摇杆取 −100..100（百分比偏移）。真实手柄轴约 8 位精度（±127），且死区通常吃掉头
10–15%，所以 1% 分辨率不损失任何可用信息，比 ±1000 少一位数字。

## 二、三种值语义（唯一需要留意的地方）

带值 token 看着形式统一，但值的时间语义分三种，解码器必须分开处理：

| 类型 | token | 缺席时 | 说明 |
|---|---|---|---|
| 增量 | `Mouse` | 无移动 | 累加量，本 chunk 移动这么多 |
| 计数 | `Scroll` | 无滚动 | 离散事件次数 |
| **状态** | `LS` / `RS` | **见下** | 杆位，是被"保持"的量 |

前两种天然是"缺席即无事发生"，与 run-length 一致。摇杆是状态量，缺席该解释为
**回中**还是**维持上一 chunk 杆位**，两者行为不同——这条会改变解码器，需要你定，
见待定决策 1。

## 三、手柄键名

按下类一律当普通键名处理，与键盘键同等，不需要任何特殊机制：

| 类别 | 键名 |
|---|---|
| 面键 | `A` `B` `X` `Y` |
| 肩键 | `LB` `RB` |
| 扳机 | `LT` `RT` |
| 摇杆按下 | `LSHold` `RSHold` |
| 功能 | `Start` `Select` |
| 十字键 | `Up` `Down` `Left` `Right` |

手柄的键名总数确实比键盘常用集多一些，但这不影响任何机制——run-length 对键名数量
不敏感，多出来的只是词表里几个 token。

`A`/`B`/`X`/`Y` 与键盘同名字母键在同一命名空间里会撞。因为一次会话只用一种设备档，
实际不会同时出现，但**解码白名单必须按设备档给**，不能给全集——否则手柄档下模型吐出
键盘的 `A` 会被当成面键 A 接受。

`LT`/`RT` 在真实手柄上是模拟量（0..100），这里先当二值键。要模拟量时按带值 token
处理即 `LT 60`，不破坏现有形式。

## 四、chunk 数不固定

现有解码器的 `expected_chunks` 从"强制对齐"降级为"可选校验"：给了就补齐/截断，不给
就按模型实际吐出的个数走。默认不给。

run-length 语义本来不依赖 chunk 总数——键在相邻 chunk 连续出现即保持按下、缺席即松开，
这套规则对任意长度都成立。放开长度不改语义，只需解码器别再强行对齐。

时间布局由环境在 prompt 里声明，模型不预测：`chunk_ms` 是单个 chunk 时长，`chunk_count`
是**建议值而非硬约束**。**控制密度** = `1000 / chunk_ms`：

| chunk_ms | 密度 | 代价 |
|---|---|---|
| 50 | 20Hz | token 少；短于 50ms 的点击丢失 |
| 33 | 30Hz | Lumine 默认；贴合人类 40ms 最小间隔 |
| 16 | 60Hz | token 翻倍；超出人类可分辨，多为噪声 |

`chunk_ms < 20` 基本只在拟合采集噪声。反向的下限受任务约束：需要精确计时的操作
（格挡、连招）撑不住 50ms 粒度。

硬约束：**MineStudio 是 20Hz 源（50ms/帧），从它构建时 `chunk_ms` 只能取 50 的整数倍**。
更细粒度需要更高帧率的数据源。

## 五、待定决策

**1. 摇杆缺席 = 回中还是维持？**（唯一会改解码器的一条）
倾向**回中**——与键的 run-length 规则一致，"缺席即松开"一条规则覆盖全部 token，
解码器不需要为摇杆开特例。代价是持续推杆时每个 chunk 都得重写 `RS x y`。若选"维持"，
则省 token，但引入了两套语义，且一旦某个 chunk 漏写就会卡住杆位不放。

**2. 超长 chunk 怎么处理**
倾向丢弃。延到下个窗口会让动作与观测错位越积越多（Lumine 已有 200ms 观测滞后）。

**3. 训练数据要不要混入变长样本**
若训练全是定长，放开长度只在推理侧生效，模型不会真用它。倾向先按单一 `chunk_ms` 训，
把变长当推理侧容错而非能力，等有多帧率数据源再说。

**4. 鼠标键名要不要跟着改**
现有 keymap 用 `mouse_left` / `mouse_right`（snake_case），新加的手柄键是 `LSHold`
（CamelCase），风格不一。倾向统一成 `MouseLeft` / `MouseRight`。纯改名，无语义影响。

**5. 视角是否离散化**
沿用自由整数，不分箱（按你之前的决定）。
