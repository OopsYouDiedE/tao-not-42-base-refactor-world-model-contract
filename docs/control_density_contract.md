# 控制契约：开放帧率与键鼠手柄统一

已定稿。相对 Lumine 有三处改动。三处均不改变 run-length 编码语义。

1. 带值操作统一为命名 token 加值。作用域是所在 tick。取消位置式 header。
2. 手柄专用键统一为 `XYAB` 等常用名。按下类按键（含 `LSHold`）按普通键名处理。
3. chunk 数不固定。

## 与 Lumine 原文的差异

Lumine（arXiv 2511.08892）的规格是固定的：感知 5Hz，电机 30Hz，每窗口 6 个 33ms
chunk，header 为位置式三整数（鼠标 `Δx Δy`，范围开区间 ±1000 像素；滚轮 ±5），
不支持手柄。33ms 的依据是实测人类 keyup 到 keydown 的最小间隔约 40ms。

| 维度 | Lumine | 本契约 |
|---|---|---|
| 带值操作 | 位置式 header，固定 3 个整数 | 命名 token，按需出现 |
| 值的作用域 | 整个窗口，200ms 内平铺执行 | 所在 tick |
| 视角输入 | 仅鼠标像素 | `Mouse` 像素，或 `LS` / `RS` 摇杆 |
| 手柄 | 不支持 | `XYAB` 等，与键盘键同等对待 |
| chunk 数 | 固定 6 | 不限 |

## 一、统一形式

    <|action_start|> ; W Mouse 10 20 ; W ; W Scroll 5 ; RS 0 100 A <|action_end|>

带值 token 后跟固定个数的整数，与键名混排在同一个 chunk 内。

| token | 值个数 | 含义 | 缺席时 |
|---|---|---|---|
| `Mouse` | 2 | 像素增量 Δx Δy，本 tick 内移动该数值 | 无移动 |
| `Scroll` | 1 | 滚轮档数，等价于重复写 `Scroll` 该次数 | 无滚动 |
| `LS` / `RS` | 2 | 摇杆偏移量，每轴 −100 到 100 | 0 0，即回中 |

全部操作都是 tick 内操作，缺席即零。按键、增量、计数、杆位使用同一条规则。解码器对
全部 token 采用相同处理方式。`LS 0 100` 表示本 tick 内 Y 方向满偏，持续本 tick。
下一个 tick 不写该 token 即回中。

`Scroll 5` 与连写五次 `Scroll` 完全等价，由模型任选。`Mouse` 与 `LS` / `RS` 不具备
这种等价关系。它们的值不是次数。

摇杆取 −100 到 100，含义是百分比偏移。真实手柄轴约 8 位精度，即 ±127。死区通常占用
前 10% 到 15%。1% 分辨率足以覆盖可用信息。

### 值挪到 tick 级的两个实测后果

在 10xx 数据的 21.7 万帧上测得以下两项。

**鼠标 token 数量增加约 2 倍。** 逐帧相机增量非零的帧占 52.4%。玩家有接近一半的时间
不移动视角。4-chunk 窗口内平均出现约 2.1 个 `Mouse` token，不是 4 个。

**±999 钳位在 tick 级几乎不再生效。** 单帧超过 999 的比例是 0.0005%，约 20 万帧中
1 帧。4 帧窗口级的同一比例是 0.0534%。单帧 |yaw| 中位数为 0，p99 为 146，最大值
1093。钳位在 tick 级几乎不改动任何数值。保留钳位的作用是拦截异常值。多数 `Mouse`
值为 1 到 3 位数。

## 二、手柄键名

按下类按键一律作为普通键名处理，与键盘键同等，不需要额外机制。

| 类别 | 键名 |
|---|---|
| 面键 | `A` `B` `X` `Y` |
| 肩键 | `LB` `RB` |
| 扳机 | `LT` `RT` |
| 摇杆按下 | `LSHold` `RSHold` |
| 功能 | `Start` `Select` |
| 十字键 | `Up` `Down` `Left` `Right` |

手柄键名总数多于键盘常用集。这不影响任何机制。run-length 语义与键名数量无关。

面键 `A` `B` `X` `Y` 与键盘字母键名称相同。一次会话只使用一种设备档，两者不会同时
出现。解码白名单需要按设备档给出。给出全集会导致手柄档下把键盘的 `A` 当作面键接受。

`LT` / `RT` 先作为二值键处理。需要模拟量时按带值 token 处理，写作 `LT 60`，不改变
现有形式。

鼠标键名统一为 CamelCase：`MouseLeft` 与 `MouseRight`，原名为 `mouse_left` 与
`mouse_right`，与 `LSHold` 等保持一致。此项仅改名称，不影响语义。

## 三、chunk 数不固定

`expected_chunks` 由强制对齐改为可选校验。传入该参数时按其补齐或截断。不传时按模型
实际输出的个数处理。默认不传。

run-length 语义与 chunk 总数无关。按键在相邻 chunk 连续出现即保持按下，缺席即松开。
该规则对任意长度成立。放开长度不需要修改语义，只需要解码器不再强制对齐。

超出期望数量的 chunk 直接丢弃，不延到下一个窗口执行。延后执行会使动作与观测的错位
逐窗口累积。Lumine 已存在约 200ms 的观测滞后。少于期望数量的 chunk 等价于剩余时间
全部松开，可以接受。

时间布局由环境在 prompt 内声明，模型不预测该值。`chunk_ms` 是单个 chunk 的时长。
`chunk_count` 是建议值，不是硬约束。控制密度等于 `1000 / chunk_ms`。

| chunk_ms | 密度 | 代价 |
|---|---|---|
| 50 | 20Hz | token 数量少。短于 50ms 的点击丢失 |
| 33 | 30Hz | Lumine 默认值。接近人类 40ms 最小间隔 |
| 16 | 60Hz | token 数量翻倍。超出人类可分辨范围，多为噪声 |

`chunk_ms` 小于 20 时主要在拟合采集噪声。反方向的下限由任务决定。需要精确计时的操作
如格挡与连招无法在 50ms 粒度下完成。

一项硬约束：MineStudio 数据源为 20Hz，即 50ms 每帧。由该数据源构建时 `chunk_ms` 只能
取 50 的整数倍。更细的粒度需要更高帧率的数据源。

训练先采用单一 `chunk_ms`，把变长作为推理侧的容错能力，不作为模型能力。训练数据全部
定长时，放开长度只在推理侧生效，模型不会实际使用该能力。让变长成为模型能力需要训练集
包含多种 `chunk_ms` 的样本，这需要更高帧率的数据源。

视角沿用自由整数回归，不做分箱。
